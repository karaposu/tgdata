## Seed and methodology
The seed is decomposition Q1–Q5: owned invocation, data handoff, durable authorities, public calling contract, and qualification. Production-task mode produces contract alternatives per question, not implementation tasks. All five are meta-decision pieces: they determine what counts as success and which intervention is necessary. Q1, Q2 and Q4 also commit intervention shape. Use a Framer-weighted contrarian rethink with full seven-mechanism coverage. A repair-first engineering mode was considered: it would concentrate on replacing `await active`, but would underweight the independently reproduced no-close wrapper loss and application continuation. A pure greenfield mode would discard demonstrated ledger/receipt/recovery work without evidence. Neither is selected.

Intuition: repeated reviews are evidence of an insufficient public contract, not evidence that every routing mechanism is defective. The surprising observation is that a successfully terminated library call can still have an unfinished application Task. Goal: an explainable ownership contract, with minimal new responsibilities and observable limits.

## Seven mechanisms, applied
1. **Lens shifting (Framer).** From implementer to receiver: data is useful only if the receiver has an address for it before cancellation. This generates P2/D2. From shutdown to application: stopping a pool grants no ownership of unrelated application cleanup, generating L2. From reviewer to deployment operator: V2 separates evidence of retained data from evidence of permission to retry.
2. **Combination (Generator).** Combine the existing owned-child outcome-as-value discipline with a library-scoped invocation witness and a caller-owned recipient (L2+D2+A2). The witness says the owned call ended; the recipient says what data was obtained; neither grants account admission or acknowledgment.
3. **Inversion (Framer).** Invert “the Task represents the read”: the Task can contain the read plus unrelated application work (L2), or eliminate active shutdown responsibility (L3). Invert “preserve the async API at any cost”: explicitly expose the recipient (P2), or replace invocation semantics with jobs (P3). Invert “more tests will save the existing architecture”: require observation of ownership boundaries rather than count (V2/V3). System-depth inversion asks whether an account pool should exist at all: a caller could perform routing outside tgdata, but that rejects the user's #17 purpose; it does not repair the local contract. Existence-axis zero is therefore tested, not silently excluded. Identity-axis: the feature remains an in-process router of already-authorized accounts, not a scheduler, durable job broker or automatic membership manager.
4. **Constraint manipulation (Framer).** ADD: each invocation must have an addressable data owner before source work, and every shutdown wait must identify whose work it joins (D2/L2). REMOVE: drop unchanged unmerged pool signatures (P2); also test dropping cancellation-prefix retention (D3), dropping concurrent close (L3), and collapsing independent stores (A1). Removing a convenience constraint is viable; removing already-requested data or safety guarantees is not an equivalent solution.
5. **Absence recognition (Generator).** Missing completion evidence: patch-level L1 avoids reading a Task's exception; redesign-level L2 ends ownership at the library's own boundary. Missing durable data recipient: patch-level D1 adds more exception attributes; redesign-level D2 supplies an owner that is not the signal. Check what already exists: source `_start_owned` holders already preserve child results; MessageBatch already supplies validated immutable content; stores already own permission and receipts. Conversely a caller Task and passive event buffer exist but do NOT serve as a stable public data recipient. No replacement store is inferred from a missing handoff.
6. **Domain transfer (Generator).** Computing-native transfer: a completion latch is not a message queue, and queue acknowledgment is not possession of an in-memory value; this independently motivates L2/D2/A2. Deliberately different domain: a courier can stop transport while a recipient keeps a parcel, but a parcel is not a signed delivery receipt; this produces D2/A2 and the need to distinguish retained content from acknowledged progress. The analogy supplies alternatives, not proof. V2 tests the actual components.
7. **Extrapolation (Generator).** Add normal wrappers, repeated closer cancellation, and an application that catches a stop then cleans up. The signal-only scheme fails even without close; the Task-join scheme grows ownership with arbitrary caller code. Extend a global result registry through many abandoned reads: retention/discard policy becomes a second storage service. Extrapolating D2 instead gives one caller-owned object per invocation; accumulation belongs to the caller, with no pool-wide registry. Generates R1 (global registry alternative) and V2.

## Real-component tests
`evidence/concept_probe.py` changes only instance-local `_operation`/`close` and adds a caller-retained adapter. No production files changed. Data, native SDK disconnects, ReadBudget charges and account/daily/backfill CAS outcomes are real. Sockets are blocked; a parent 35-second watchdog bounds the experiment.

46 histories pass: six lifetime contrasts (three caller-Task joins remain waiting; three invocation-witness joins finish), 18 ordinary completed-batch cancellations across raw/daily/backfill × direct/shield/gather-values × observer order, six 100-record/FloodWait7200 cancellations before/after actual account settlement, twelve ordinary provider-fault account-settlement histories, and four progress-publication fault histories. Charges remain 1 or 200; no second-account fetch is substituted. Cancellation remains actual Task cancellation. True cancellation can leave no pending group receipt while the recipient still holds data. Ordinary local failures retain existing real pending behavior. Before/after commit state remains distinguishable.

The first run failed an overly early eight-loop-turn “close completed” observation. That log is retained as `concept-probe-initial.txt`. Waiting up to 500 loop turns lets actual native retirement finish while the application remains blocked; the final run passes all 46. This adjustment waits for the claimed event; it changes neither expected data nor production behavior. It is not a speed or timeout guarantee.

Limit: the adapter captures at the public coroutine exit, proving independent ownership is feasible for tested outcomes. It is NOT a complete early-publication implementation, a full prebuild, or proof for arbitrary scheduling/storage faults. It does not qualify prestart handle behavior, invalid/reused recipients, safe provisional updates or byte bounds. Those are contract and later qualification obligations, not secretly implemented features. Only Python3.11.10/Telethon1.45.0 were executed.

## Assembly and axis coverage
The selected assembly is L2+D2+A2+P2+V2. It has two local ownership facts rather than a new scheduler: **the library knows when its invocation ends; the caller knows where its data lives**. Durable authorities remain unchanged.

| Axis | Variants actually tested/reasoned | Selected contract element and trace |
|---|---|---|
| Lifetime | caller Task join, invocation witness, idle-only close | Private owned-invocation completion independent of application continuation (L1–3) |
| Data ownership | exception, caller recipient, refetch, journal, global registry | One caller-owned destination per invocation; no consumption by close or observations (D1–4/R1) |
| Calling form | unchanged hidden guarantee, explicit recipient, cooperative jobs | Explicit recipient for the canonical guaranteed form; reject silent weaker facade (P1–3) |
| Durable authority | unified transaction, separate stores, delivery-derived permission | Existing admission/quota/receipt records keep separate meanings (A1–3) |
| Qualification | more examples, ownership histories, live-only | Boundary matrix plus retained offline suite; live gate separately pending (V1–3) |

The public contract must say: allocate/retain a recipient before invoking a data-producing pool call; bind it to at most that invocation before I/O; normal return/error/cancellation semantics remain observable; complete validated data is accessible without re-awaiting a cancelled Task. An invocation that never starts performs no I/O and has no produced data. Required one-shot binding, invalid reuse rejection, terminal status and disposal rules must be qualified rather than inferred from the small adapter. Exact names are not an implementation plan.

A recipient carries at most one current batch under existing batch limits, not an unbounded event history. This is a cardinality/lifetime bound, NOT a byte-size bound that the current MessageBatch schema does not promise. It must not retain live clients, caller Tasks, credentials or exception traceback graphs. After finalization it is stable and retrieval is read-only; keeping or discarding it is caller-owned. Process death can lose unpersisted in-memory data; real durable pending state remains replayable by its existing API.

Availability is not publication: actual data may become available while final settlement remains unfinished. “Ended” is about this invocation, not receipt confirmation, account eligibility, or an application's following cleanup. A full successful return must not be downgraded merely because close happens later. A cancellation/error prefix is conservatively interrupted; it cannot invent end-of-history or an acknowledgment receipt. The underlying source-owned span can end before caller-owned progress publication ends; close need not seize ownership of all state-only operations.
