## The concepts this feature lives or dies by — question each one against the code

### 1. An observer never breaks the observed
The health layer wraps every public `TgData` method that talks to Telegram, and adds report calls inside engine `except` blocks.
- Can anything in it change what a caller receives: the exception type and identity, the return value, or a loop that was built to keep going?
- Can a broken callback, a broken ledger, or a logging misconfiguration reach the caller?
- Can a filter on Telethon's own logger ever raise into Telethon's request?

### 2. Verdicts come only from Telegram's own names
- Is the classifier exact on Telethon 1.45.0: every listed name, no category fallback, file references excluded?
- Is the cause-chain walk correct for each wrapper tgdata uses, including implicit `__context__` and `raise … from None`?
- Can a non-verdict — a transport error, a 400, a first login, a user's own exception — become an event?
- Can a verdict be lost?

### 3. Attribution: account, call, task, group
Context variables follow tasks, and Telethon's background tasks — the updates loop, keepalive, the sender loops, event handlers — inherit the context of whatever call ran `connect()`.
- Is every event attributed to the right `TgData`, the right call, and the right group?
- Does it stay right with several `TgData` instances in one process, with nested public calls (`poll_for_messages` → `get_messages`), and with user tasks created during a call?

### 4. Recovery: "ok" only when a condition has ended
This is the feature's central promise (desc criterion 6).
- Does every path that emits `ok` have evidence that the condition ended?
- Look for any way a call can complete "successfully" and recover a verdict without Telegram having answered after the verdict was recorded:
  - concurrent calls on one `TgData`;
  - calls that send no request at all;
  - calls that swallowed the verdict themselves;
  - health and validation calls.
- A false `ok` is the failure class step 3's critic rated Medium. Rate this class on the same scale.

### 5. Counted once
- Is each Telegram answer reported exactly once across nested boundaries, the poll loop, the fetch loop's give-up, and engine handled and swallowed sites?
- Can the counted-once mark suppress a *different* later occurrence?

### 6. Resource lifetime
The design stores objects in context variables, and long-lived tasks Telethon creates inherit those contexts.
- What does a finished call keep alive, through which reference, and for how long: tasks, results, monitors, `TgData` instances?
- Measure it with a probe.

### 7. Logging side effects
A filter and a sentinel level are installed process-wide on `telethon.client.users`.
- Is any user's logging output changed, under default config, explicit levels, `dictConfig`, `logging.disable`, or handlers on ancestors?
- Does the event mirror on `tgdata.tgdata.health` reach `log_file=` users as the docs claim?

### 8. Public behaviour changes
Three are deliberate:
- `poll_for_messages` stops on terminal verdicts and propagates callback errors;
- `validate_connection` asks Telegram when `get_me()` returns `None`;
- `health_check` reports and recovers.

For each, ask:
- Is it exactly what the desc and README say?
- Does it break an existing caller in a way they cannot see coming?
- Does it change request counts or latency on the happy path?

### 9. Test validity
For each claim the new test makes, ask whether it *observes* the behaviour or *supplies* it. A scripted error or a stand-in engine supplies the error. What matters is whether the code under test then does the real thing, or the test hands it the state it asserts on.

### 10. Docs accuracy
- Does every sentence the README and docstrings now state hold in the code, including limits and defaults?
