## The concepts this plan lives or dies by — question each one

### 1. The credential's lifecycle
The session string carries the account's auth key: full access to the account.
- Follow the key through every path: built, loaded, saved at connect, reset on a data-centre switch, regenerated, saved at close, deleted on log-out.
- Can a login be lost or replaced silently?
  - by two clients, or two processes, writing the same stored session;
  - by a client that started before a login completed;
  - by a key Telethon regenerates.
- Is the plan's and the desc's claim that "the login is never lost" true in every case it covers?
- Can the key leave the store by any other route: logs, exception text, reprs?

### 2. Fidelity — what is stored versus what is needed
- The desc promises the *group cache*. The in-memory session caches every entity a response carries, message senders included.
- What does tgdata actually need across a restart? What does the plan store?
- Is anything Telethon reads at `connect()` missing? Is anything stored that nothing reads?

### 3. Cost and growth
The design keeps the whole session in memory and rewrites the whole string on every changed save, where Telethon's file session writes rows incrementally to disk.
- Measure size, dump time and memory for a realistic account: a scraping account sees many message senders.
- What does the minutely save cost when the cache changes every minute?
- What happens for a process holding many accounts — the issue's own motivation?

### 4. Failures are loud — and safe
- Load: does every failure raise before connecting, and is it never mistaken for a first login?
- Save:
  - is every failure logged and never raised into Telethon's loops?
  - what exactly gets logged?
  - can the failure log carry the session string?
- Delete: is its failure handled sensibly?

### 5. Concurrency and the event loop
The store's methods are synchronous and run on the event loop. What does a slow store do:
- to the loop, to Telethon's keepalive and updates loop;
- to other accounts in the same process?

Two clients, or two processes, on one stored session: is "the later save wins" safe for the cache and for the login?

### 6. The string contract
- The store receives "a string". What may a store do with it without breaking it?
- Is it robust to a store that parses or normalises JSON — for example, large integers read as floats?
- Is it versioned, and deterministic?

### 7. The default path
- Is the default byte-identical: the same name reaching Telethon, the same `.session` file?
- Is the `first_login` logic from `c72eab4` unchanged for both stores and files?

### 8. Telethon's contract
- Does the store-backed session honour every abstract session member and Telethon's call order: flush, then `close()`; disconnect, then `delete()`; restoring update states and the self-id row at `connect()`?
- Does any tgdata or Telethon code path assume a `SQLiteSession` — a `filename`, `list_sessions`, or row-level writes?

### 9. Test validity
For each planned test, ask whether it observes the behaviour or supplies it. A scripted connection supplies Telegram; a stand-in client supplies `connect()`. Name each success criterion that no planned test exercises through Telethon's real code.

### 10. Docs
- Will the README tell users what they must know to run this safely: that the methods run on the event loop, what the string contains, two clients of one session, and calling `close()`?
